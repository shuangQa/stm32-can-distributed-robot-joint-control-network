# 第一版本

## 标准的代码结构

MCU  \-\>  HAL/BSP\(硬件抽象层）  \-\>  Drivers（设备驱动层）  \-\>  Service\(服务层）  \-\>  Application（业务层）

1. 第一层——BSP（板级操作包）——只负责操作硬件寄存器

2. 第二层——Drivers\(设备驱动层）——对硬件功能上的操控，不负责为什么操作硬件，只负责实现控制硬件可执行的一个个功能模块

3. 第三层——Service\(服务层）——服务层是服务业务逻辑的，做的就是怎么实现业务逻辑，可以认为是设备驱动层与业务层的连接桥梁

4. 第四层——Application\(业务逻辑层）——系统级的功能模块，整体、系统之下的紧挨着的那一层，如机器人，那么业务层就是机器人向前动一下，机器人向后动一下，可以理解为**主语是系统的动作或活动或指令就是业务层**

- 实际中，各层之下根据需求细分，各层之间也可适当增减

- 如**common一般代表公共通用层，或者说不止一个部分要用的内容的集合层****，最开始我以为是类似“其他层”，但是不是的，就是通用层，这里放置是整个项目各部分没有区别的，或者说较上层次的一些东西，这样设置的目的是，对整个系统的某些配置更改时，之间到这里就可以了，类似于可读性好，维护性好，类似将常用值用常量定义的一个作用，****用于简便开发的**

## 初步设计的软件目录结构

HAL库\+BSP——设备驱动——业务逻辑

```C
App
│
├── DeviceManager
├── Protocol       //通信协议解析模块
├── Heartbeat
├── StateMachine
└── MotorControl

Driver
│
├── Motor
├── Encoder
├── OLED

BSP
│
├── CAN
├── PWM
├── GPIO

Common     //通用层
│
├── Types   //通用数据类型定义，如typedef uint8_t u8
├── Config    //全局项目配置
└── ErrorCode     //全局错误码
```
