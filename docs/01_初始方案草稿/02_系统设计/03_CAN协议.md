注册报文:  ID=0x100

# 第二版本（ID\+数据）

## 初步设想

首先，ID部分，有两种想法：

一种ID用以区分报文类型，如第一版本中的注册报文和心跳报文则ID不同，不关心接收节点；

第二种想法，以不同的节点使用不同的ID，这样的好处是，发送如电机控制报文时不需要所有的电机节点都接收，但是坏处是，如果想要同时控制多个电机节点的话，需要发送多条报文，不过不同位置的电机执行相同的动作还好，执行动作的幅度一般应该不会相同，所以其实这里也不用考虑，或者可以说，以不同类的节点区分使用不同的ID，对于近似完全相同的节点，归为一类。

但是，考虑到扩展性要求，如果使用第二种方法，一个设备一个ID，那么随着不断扩展更多的功能节点，ID太复杂太多了，开发时候岂不是很容易就用错了，都记不住哪个ID对应哪个设备

而第一种ID，相当于将ID再次进行归类，传统意义上的ID由主控维护，是大类，然后每个ID下面有一些实际意义上的分支ID，由节点自己判断，这样的话，首先整个结构很清晰，还是树状结构，其次就是扩展时可以直接扩展一个整体下来，就是说这里的分支ID可以继续延伸为分支的分支ID，这样的话，可以直接在CAN总线上扩展进来一个模块，其**内部的细节并不需要主控关心**

**每一层只关联到三层：自身层，上一层，下一层。且对上下层尽量只通信，不处理，处理只对自身层，自己的事情自己做，结构的事情大家做，我觉得这是扩展性和系统性的体现。我觉得这是很合适的**。

## 具体进一步设计CAN协议

### 报文归类、设计

对于我的一主控两节点结构，实际上的报文传输都在主控与节点之间，节点与节点之间并不需要

主控：监测状态，控制运动，注册节点

节点：反馈状态，接收控制，发送心跳表示在线/注册

CAN数据段是0\~8字节内容

### 控制报文

#### 需求分析

控制 指定节点电机 以一定转速 开始/停止转动

发送方：主控

接收方：节点

#### ID

0x300

#### DATA

节点编号NodeID——第0字节（uint8\_t范围0\~255）

目标转速TargetRPM——第1、2字节（int16\_t \-32768\~\+32767）

使能位Enable——第3字节

第4\~7字节暂不使用

### 状态报文

#### 需求分析

状态报文的目的是提供必要信息给主控来检查是否出故障

向主控告知 某个节点 当前速度 当前输出的PWM（主控拿来结合判断当前是否状态正常，比如最大PWM还是达不到速度） 故障信息 等状态

但是这里的PWM判断故障可不可以在节点内进行?然后结果直接输入到故障信息里

还是要上传PWM，故障判断在节点内进行当然更好，这样更体现分布式、更有自己对自己负责的体现，上传PWM，只是为了给故障状态提供一个对应的证据，

**当故障出现后，我们不止关注故障本身是什么故障，更关注的是故障的原因**

所以上传证据\+结果，证据数据也传到主控后，主控在显示出来，可以据此分析故障原因进而解决故障

发送方：节点

接收方：主控

#### ID

0x400

#### DATA

NodeID——第0字节

ActualRPM（当前转速）——第1、2字节

PWM——第3字节

State【（自检出的）状态】——第4字节，是否有故障

FaultCode（故障码）——第5字节，显示具体是什么故障

第6\~7字节暂时不用

### 注册报文

#### 需求分析

发送给主控 某个节点（节点编号） 节点信息？

发送方：节点

接收方：主控

#### ID

0x100

#### DATA

NodeID——第0字节

NodeType——第1、2字节

其他字节先不用

### 心跳报文

#### 需求分析

隔一段时间发送一个信号向主控表示设备还在线

发送方：节点

接收方：主控

#### ID

0x200

#### DATA

NodeID——第0字节

State——第1字节

其他字节先不用

## 预留设想

ACK报文，在主控发出指令后，节点返回给主控接收到指令，这样能及时知道是否接收有错误
