# 01\_状态机设计\.md 

# Joint状态

Init——初始化状态。设备刚接入CAN总线，刚通电，完成自身的初始化，初始化结束后发送注册包进入注册状态

REGISTERING——注册状态。设备刚初始化完成，向外发送注册消息并等待主控应答确认，未确认则重新注册

ONLINE——在线正常状态。注册完成，收到确认后进入在线状态，心跳正常上报，可以接收主控的控制消息，可以执行运动，内里可再细分设计：空闲状态，运动状态。发生故障后进入故障状态。

FAULT——故障状态。设备在线但是发生异常：过流、堵转、编码器异常、PID溢出等，此时应停止电机输出，上报故障的各种对应标志。故障解决后进入正常在线状态

> 状态流转逻辑：
> 
> 1. 上电 → Init → 发送注册包 → 进入`REGISTERING`
> 
> 2. 收到主机注册应答 → 切到`ONLINE`，开始周期发心跳
> 
> 3. 运行中一旦检测硬件 / 软件异常 → 跳入`FAULT`故障态，电机停机保护
> 
> 4. 连续收不到心跳 → 主机 Device Manager 把此关节置回逻辑上的`OFFLINE`
> 
> 

# Master状态

INIT——初始化状态。主机上电启动，完成各部分硬件（比如CAN外设，OLED），各部分软件模块（设备管理、监控器、命令管理）初始化

RUNNING——正常运行状态。初始化完成，系统正常工作：设备注册、状态监测、发送指令等

FAULT——主机故障状态。主机本身发生错误，如CAN总线报错等，停止进行运动控制，向OLED输出故障原因

## Master状态2\.0

- 这里我了解到，一般有两种模式的状态，严格启动模式：初始化后必须所有关键节点正常注册，才可运行；动态管理模式，初始化后直接正常运行，随时接入设备注册。

- 由于我的项目重点体现CAN总线下的设备发现、设备注册、在线监测与扩展能力，因此采用动态管理模式，但是，为了更贴合实际工程，我选择一个没什么实际意义的状态，依旧采用WAIT\_DEVICE状态但是内部肯是一些可以合并到其他状态的内容或者单纯延时一会，来起到使结构完整的作用。

INIT——初始化状态。主机上电启动，完成各部分硬件（比如CAN外设，OLED），各部分软件模块（设备管理、监控器、命令管理）初始化

WAIT\_DEVICE——等待必要/基本设备全部正常注册状态

RUNNING——正常运行状态。初始化完成，系统正常工作：设备注册、状态监测、发送指令等

FAULT——主机故障状态。主机本身发生错误，如CAN总线报错等，停止进行运动控制，向OLED输出故障原因
